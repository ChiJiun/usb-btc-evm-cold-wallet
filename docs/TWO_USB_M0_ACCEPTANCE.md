# Two-USB M0 exact-image / physical acceptance (#1, #43, #66)

**Scope:** USB-A = x86_64 UEFI Buildroot OS + `COLD_VAULT` (two GPT partitions); USB-B = independent FAT32 `TX_TRANSFER`. This is the **two-device M0 CLI/text appliance**, not PR #80's single-USB three-partition/GUI acceptance. Use only public/expendable test wallet and testnet funds. No signer, vault, runtime, CI, flash or format automation is provided here.

**Current record (documentation-only, 2026-11-23):** all acceptance cases **NOT TESTED** until a named tester supplies verifiable observations. M0 **BLOCKED**. A successful docs-only `CI / Required` check is a documentation gate; it is not a Live USB build, QEMU result, or physical acceptance. The following commands and identifiers are instructions and expected values, not an assertion that they ran on this PR. Never substitute a historical CI result or QEMU boot for final image-byte or physical acceptance. Never include mnemonic, passphrase, private key, vault bytes, full sensitive payload, unredacted serial or policy anchor secret in evidence.

## A. Exact source → image / kernel provenance (Linux x86_64)

On a disposable, **clean Linux x86_64 checkout of the selected source commit** (full 40-hex `git rev-parse HEAD`, never just the moving `main` label), verify that `git status --porcelain` is empty and that `test -f Makefile && test -x scripts/verify_uefi_boot.sh && test -x scripts/verify_image.sh` succeeds. Run and preserve stdout/stderr and exit codes:

```sh
git status --porcelain
git rev-parse HEAD
make prepare-sources
make image
make verify
sha256sum build/output/images/usb-cold-wallet.img build/output/images/bzImage
(cd build/output/images && sha256sum -c usb-cold-wallet.img.sha256 && sha256sum -c bzImage.sha256)
make reproducibility-check
cmp build/reproducibility/run-1.sha256 build/reproducibility/run-2.sha256
make verify
scripts/verify_uefi_boot.sh
sha256sum build/output/images/usb-cold-wallet.img build/output/images/bzImage
# Confirm these two values equal BOTH clean-build run manifests.
(cd build/output/images && sha256sum -c ../../reproducibility/run-2.sha256)
```

`make reproducibility-check` **deletes generated `build/output` and builds twice** in the same output path; run only on a disposable build workspace with no local artifacts to preserve. It compares image and kernel hashes, and the **final generated bytes** must be reverified afterward. Save both `build/reproducibility/run-{1,2}.sha256`, CI job URLs, source SHA, build host architecture, tool versions, actual digest values and the SHA-256 of any downloaded artifact. This is two sequential local clean builds; #88's **separate-runner parallel clean-build equality / Required gate** is an additional CI assertion and must not be replaced by the local check. The mere existence of `.sha256` files proves nothing about downloaded artifact authenticity.

QEMU/OVMF: install the host `qemu-system-x86_64` plus a matching OVMF CODE/VARS pair; run `scripts/verify_uefi_boot.sh` from repository root after producing the **same final image**. The script uses a disposable variables store, `-net none`, snapshot USB disk and demands serial `USB_WALLET_UEFI_AUDIT_OK`; `USB_WALLET_UEFI_AUDIT_LOCKDOWN`, timeout or premature exit is FAIL. The script does **not** test interactive transactions, USB-B or physical boot. Save the command exit code, console output, tool/firmware versions, image hash and bounded diagnostic path `build/reproducibility/uefi-smoke.log` (written on failure). Only claim CI evidence for a run that identifies the tested source and image bytes, with matching hash artifact.

**Current #88 CI output (main, inspected at `024dae15c9a3e1100ccd7ee3df26974eeea07acc`):** `.github/workflows/live-usb-build.yml` runs independent `clean-builds` matrix `[1, 2]` on separate `ubuntu-24.04` runners, then `verify-and-publish` checks both `run-{1,2}.sha256` files for byte-identical *raw image and kernel* hashes, checks the downloaded runner-2 files against those manifests, boots that raw image with QEMU/OVMF, and packages `testnet-only-NOT-A-RELEASE-usb-cold-wallet`. Its 3-day-retention artifact includes `usb-cold-wallet.img`, `usb-cold-wallet.img.xz`, both `*.sha256` files, `run-1.sha256`, `run-2.sha256`, and `ARTIFACT-MANIFEST.txt`. The manifest records `commit_sha`, `event_head_sha`, `workflow_run_id`, `workflow_run_attempt`, `workflow_ref`, `image_sha256`, and `compressed_image_sha256`. The published artifact is **TESTNET ONLY / NOT A RELEASE**, unsigned and not independently attested.

For the **selected image-producing source SHA**, record both independent runner job URLs/conclusions, workflow run ID/attempt, artifact ID/name, exact raw/kernel SHA-256 from both manifests, the byte sizes, and the downloaded artifact identity; do not reuse a run from a different SHA or treat a docs-only required check as the dual build. Verify all of these against the source SHA and run shown by GitHub. Verify artifact contents on a trusted machine after extraction (these commands execute from the directory containing the artifact files):

```sh
sha256sum -c usb-cold-wallet.img.sha256
sha256sum -c usb-cold-wallet.img.xz.sha256
awk '$2 == "usb-cold-wallet.img" {print}' run-1.sha256 | sha256sum -c -
awk '$2 == "usb-cold-wallet.img" {print}' run-2.sha256 | sha256sum -c -
cmp run-1.sha256 run-2.sha256
xz --test usb-cold-wallet.img.xz
xz -dc usb-cold-wallet.img.xz | cmp - usb-cold-wallet.img
sha256sum usb-cold-wallet.img usb-cold-wallet.img.xz
```

Require the actual `usb-cold-wallet.img` SHA to agree with **both** runner manifests, `usb-cold-wallet.img.sha256`, and the manifest `image_sha256=`; require the compressed SHA to equal `compressed_image_sha256=`. The `bzImage` SHA must match both runner manifests (the verified artifact intentionally does not include `bzImage`; use the independent manifests and the `verify-and-publish` job's verified staging/QEMU logs). Do not run `sha256sum -c run-{1,2}.sha256` verbatim on this downloaded artifact: each manifest also names the **absent** `bzImage`. Confirm manifest `classification=TESTNET ONLY / NOT A RELEASE`, exact `commit_sha` and `event_head_sha`, run ID/attempt and GitHub workflow identity. An `xz` checksum verifies compressed bytes, while the *raw image* SHA is the identity to be flashed. Missing/expired artifact, mismatched hashes, absent actual raw bytes or untrusted run identity => **BLOCKED**, not PASS. A hash inside the same downloaded bundle alone does not authenticate its origin.

## B. Two physical media, Windows and offline operator sequence

1. On the Windows host, identify both physical devices with PowerShell `Get-Disk`, `Get-Partition`, `Get-Volume` (and `Get-FileHash -Algorithm SHA256 -Path $imagePath` after explicitly setting `$imagePath` to the **local raw file**). Confirm model, capacity, bus, sector size, partitions and device ancestry on **each insertion**; no fixed PhysicalDrive number or drive letter. PR #80's `scripts/physical_usb_inventory.ps1` is on main since #80 was merged, but it verifies only the **single-USB three-partition** layout. Never use its single-USB partition expectations for M0.
2. A human operator, after positive hardware identification and backup, uses a trusted GUI imaging application to write the verified image to **USB-A** (erases USB-A). Capture the application readback result and independently audit actual GPT/ESP/`COLD_VAULT` on the **written media**; the host raw-file SHA by itself does not validate flashed media. Provision **USB-B** as FAT32 volume label `TX_TRANSFER` separately, only after confirming its physical parent differs. This document intentionally supplies **no destructive flash/format commands**. On every re-insertion rediscover both actual parent disks and all partitions; reject duplicate labels, GPT disk GUIDs/PARTUUIDs, ambiguous matches, wrong filesystem, wrong USB bus, or a transfer partition that shares USB-A's parent. Record offset/size/GPT type and unique GUIDs. For this exact `genimage.cfg` layout: USB-A GPT disk GUID `f1448aa1-28cc-54bf-8fdd-3008514c0ab5`, boot PARTUUID `e2bd6d1b-8de5-502d-a897-c53a8e60f46b` (EFI type, `USBCOLD_EFI`), vault PARTUUID `18f1c36f-d5c0-5052-9cd2-03e9c2a48f00` (Microsoft Basic Data, `COLD_VAULT`). The static image verifier checks structure but does not authenticate the *physically read-back* disk or guarantee full backup-GPT/CRC verification; preserve independent written-media evidence. USB-B is a **different** disk, not a third USB-A GPT partition.
3. Boot USB-A on a real x86_64 UEFI host with USB-B attached. Record exact firmware/version/Secure Boot setting, cold boot timing and startup audit. Inspect `/proc/mounts`, `/proc/swaps`, `/proc/net`, resolved kernel config, unique PARTUUID ancestry and lockdown status using read-only appliance/runtime facilities. Expect RAM-only root, no networking/swap, restricted vault mount, no unintended writable internal drive; a failure must forbid signing. Preserve redacted audit transcript, not a claimed PASS based on seeing a menu.
4. Use menu **1** to create a *disposable testnet-only* encrypted wallet (the current appliance generates a **new** random mnemonic; it does not let the menu import a public fixture), menu **2** to compare public addresses, and menu **7** to create policy. Keep the printed policy SHA-256 on **independent paper** and enter it from that paper on signing; never rely on the USB to supply its own trust anchor. Reboot to verify vault persistence and wrong-password rejection. Any cross-boot anti-rollback claim additionally needs independently trusted monotonic state and observed test results; policy hash alone cannot establish it. Do not record mnemonic, paper anchor, vault password or vault bytes.
5. **Windows → USB-B → offline signer → USB-B → Windows, Sepolia:** use the *checked-out* Companion's documented command/GUI, record the actual syntax from its help, create a type-2 **native** transfer on `chainId=11155111`. Record a sanitized request ID/digest; on the cold text appliance independently review account, recipient, value, nonce, gas limit and maximum fee before explicit approval. Import the signed response online; verify account, chain, request binding, transaction fields and recovered signer. Broadcast only after separate deliberate user authorization; record tx hash and receipt only if actually broadcast.
6. Repeat the round trip for **Bitcoin testnet BIP84 PSBT v0**. Cold side checks network, account, UTXOs, recipient, change, amount and absolute fee before manual sign. Online side verifies the signed response, signatures and original PSBT semantics, finalizes/extracts if supported; only explicit user broadcast produces a recorded txid. Record unsigned PSBT digest and request ID, never fabricate a txid if no broadcast occurred.
7. For negative cases use **reproducible, disposable** test media only. Test USB-A/B swap, wrong parent, duplicate label or PARTUUID, wrong partition, malformed/truncated request, altered recipient/amount/chain/account, wrong policy anchor, replay after reboot, USB-B removal and interruption during request/response/vault writes as **separate cases**. Observe fail-closed effects and absence of unauthorized signature/broadcast. Restore from known clean test state between injections; do not infer anti-rollback from authenticated encryption or USB file metadata.

For actual offline operation the checked-in `src/usb_cold_wallet/appliance.py` implements menu **3** Sepolia, menu **4** BTC, menu **5** transfer re-scan and menu **6** power-off; it calls `python -m usb_cold_wallet.cli` internally. Record the actual online Companion commands/help from the tested commit rather than inventing a Windows CLI. An unrun command is not evidence. Avoid copying PR #80's single-USB reboot/GUI steps into this two-USB acceptance.



### Physical readback and separation — safe reference commands

Windows PowerShell (read-only; run on **each** USB insertion, inspect all candidates rather than assuming one drive number):

```powershell
Get-Disk | Select-Object Number,FriendlyName,BusType,PartitionStyle,Size,LogicalSectorSize,Guid
Get-Partition | Select-Object DiskNumber,PartitionNumber,Guid,GptType,Offset,Size,DriveLetter
Get-Volume | Select-Object DriveLetter,FileSystem,FileSystemLabel,Size
```

After human confirmation of **the actual whole USB-A disk** on a trusted Linux host, independently compute a SHA-256 of precisely the first `stat -c %s` image bytes on USB-A. This is **read-only**; substitute the correctly resolved `/dev/disk/by-id/...` path and do **not** use a partition path. Use Bash with `pipefail` so a truncated read fails. Record the exact device path, full `lsblk -o NAME,PATH,TRAN,SIZE,LOG-SEC,FSTYPE,LABEL,PARTUUID,PARTTYPE,PKNAME` inventory, exit code, observed hash and whether it matches the trusted raw image SHA:

```bash
set -o pipefail
image=build/output/images/usb-cold-wallet.img
# Set only after manual model/capacity/USB-parent verification:
# device=/dev/disk/by-id/<confirmed-whole-USB-A-disk>
lsblk -o NAME,PATH,TRAN,SIZE,LOG-SEC,FSTYPE,LABEL,PARTUUID,PARTTYPE,PKNAME
# Run only after assigning device to the verified whole-disk path:
if [ -z "${device:-}" ]; then echo 'STOP: verify USB-A parent and set device first' >&2; exit 1; fi
sudo dd if="$device" bs=1M iflag=count_bytes count="$(stat -c %s "$image")" status=none | sha256sum
```

The `image` path above assumes a locally built raw image; when using the #88 downloaded artifact, set `image` to that **verified extracted raw .img** instead. Compare actual image and readback SHA-256 and total bytes. Keep readback, GPT/volume ancestry and x86_64 UEFI cold-boot as **separate evidence cases**. A matching readback does not establish that the host actually booted USB-A.

- **PASS**: identified tester and UTC date; exact tested source/image and hardware; actual command/action executed; observed outcome matches expected security invariant; exit code (when applicable); SHA/request/tx identifier when applicable; at least one **existing, inspectable evidence file with verified SHA-256** and explicit security decision. A planned command, nonempty free-text claim or CI success with no image identity is insufficient.
- **FAIL**: executed case violates expected behavior. Include redacted observed behavior, failure stage and evidence.
- **BLOCKED**: could not execute because a specific prerequisite is absent (identify missing raw image, funds, trusted replay anchor, hardware, incompatible firmware, etc.); no claim of successful execution.
- **NOT TESTED**: not attempted, or no verifiable execution evidence. All physical hardware cases start and remain here until physical observations exist. A PR CI run can only support CI-scoped cases on matching source/image bytes.
- Report coverage as **verified PASS / total required cases**, and separately **executed / total**; optional broadcast tests must be counted separately, not silently removed from denominator. No aggregate PASS if a required case is FAIL/BLOCKED/NOT TESTED.
